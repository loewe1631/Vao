# Windows 通用文字入口验证器

这是独立实验工具，不是新的 Vao 安装包，也没有接入日用回填。只输入固定短句 `Vao 通用输入测试 🙂 A7`，没有麦克风、模型、剪贴板操作或默认输入法变更。不读取用户正文、窗口标题或 UIA Name/Value/GetText。关闭控制台即可退出，无安装或后台服务。

先从托盘退出 Vao；目标应用保持普通权限。在记事本、网页编辑框、聊天草稿或办公软件中准备**空白、未保存的测试文档**，不要在真实会话、密码框或需要保留的选区中操作。

1. 双击 `Start-Input-Lab.cmd`，看到中文“已就绪”后保持控制台运行。若显示“验证器已结束”或退出码，工具已停止，继续按快捷键不会输入。
2. 在要测试的空白输入框里点击放置光标，按 `Ctrl+Alt+F8` 捕获目标。
3. 按 `Ctrl+Alt+F9` 并松开按键，工具恢复原窗口并且只提交一次固定短句，不按 Enter。
4. 文字入口成功后，再按 F8 捕获，切到另一个应用，按 F9 检查能否返回原输入处。每次 F9 后必须重新 F8，目标60秒到期。`Ctrl+Alt+F10` 取消。
5. 完成后关闭控制台，报告保留在旁边的 `reports` 目录。反馈“应用 / 短句是否完整出现 / 切应用后是否回到原框”。不用填写或发送真实文字。

一轮实验只区分两件事：Unicode 文字入口是否有效，以及系统保存的窗口/焦点能否恢复。日志中的事件入队数量不代表文字已进入目标，实际结果需要看输入框。若同一窗口内的编辑位置无法被识别，工具只记录窗口级证据，不会把它当作可靠的光标恢复。

此实验没有字段全文快照或内容冲突保护。即使实验成功，也不能直接作为普通模式无条件后备；还需完善精确输入位置与应用收据、内容冲突和多行/格式验收，再接回录音。工具遇到权限、窗口失效、已知焦点/光标变化、按键未松开或系统拒绝激活时停止，不重试可能的部分输入。

跨应用返回时，窗口到前台和编辑区恢复焦点可能先后发生。工具最多等待约1.5秒；若250毫秒后仍没有原生焦点，且保留了原来聚焦的UIA元素，只对该元素请求一次系统 `SetFocus`，随后仍须确认原窗口、原控件、已有光标及UIA身份一致。已知另一个控件有焦点时立即停止，不调用该请求。超时不发送文字；不通过坐标点击、输入队列挂接或重新搜索别的控件恢复。

GitHub 的 `--self-test` 只在自己创建的合成应用进程中读取测试文本，验证中文/emoji、原进程恢复、选区、光标、失效、密码保护和无 Enter/剪贴板操作。它不证明 dsh、WPS 或浏览器现场通过。

回归检查还创建自有合成控件并通过真实 UI Automation 检测：不支持 Value/Text 的控件必须安全记为“不支持”，支持这些接口的输入框仍能恢复和收到完整短句。UIA 返回成功状态不保证接口非空；取接口时同时检查返回值和指针。

启动阶段、快捷键注册失败、每次捕获/提交开始与结果都会写入 `reports`，启动脚本另保存进程退出码。即使某个外部 UIA 提供程序崩溃，也能区分最后进行的是启动、捕获还是提交。控制台显示中文状态，不弹窗抢走目标焦点。

焦点恢复报告还包含等待耗时、空焦点采样次数、是否请求原UIA元素恢复焦点及其HRESULT，区分窗口激活、焦点恢复和文字事件提交。自有测试进程覆盖延迟恢复、需要明确焦点请求、始终缺少焦点，以及后来恢复到其他控件的四种情况。

依据：[KEYBDINPUT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-keybdinput) / [SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)。
